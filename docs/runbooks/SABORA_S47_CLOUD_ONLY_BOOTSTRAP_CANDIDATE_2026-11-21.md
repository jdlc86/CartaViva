## Decisión del propietario y separación de confianza

El **ordenador doméstico del propietario no participa** ni ahora ni en operaciones futuras. Tampoco se necesita mantener una conexión SSH de ChatGPT. El **cliente SSH se ejecutaría en GitHub Actions**, exclusivamente en `jdlc86/CartaViva`; usa una clave temporal **diferente** de `sabora-release`, `sabora-maint`, de las claves Ed25519 de firma propietaria y de cualquier proyecto ajeno. La privada se generaría y custodiaría mediante un entorno cloud autorizado y se almacenaría **solo como secreto restringido del environment** `sabora-bootstrap-stage`, nunca en Git, chat, logs, VPS, Gateway ni ordenador doméstico. Su pública se instalaría mediante una operación de aprovisionamiento explícitamente autorizada, nunca transfiriendo la privada al VPS. No se presupone que el conector actual pueda crear secretos GitHub ni iniciar manualmente `workflow_dispatch`.

No es **cero intervención**: aún deben realizarse, con permisos efectivos del propietario y sin PC doméstico, una ceremonia inicial de custodia de secreto GitHub, verificación independiente de la huella del host, instalación del receptor y pública en el VPS. Esto puede hacerse mediante interfaz web/GitHub Codespaces/cloud bajo autorización separada; disponibilidad y permisos de Codespaces y GitHub environment se deben comprobar, no presuponer. El receptor se podría aprovisionar vía operaciones tipadas de Gateway **solo si** la herramienta admite la restricción exacta, el propietario autoriza **ese aprovisionamiento**, y nunca se utiliza Gateway para transmitir los lanzadores. Si no, operador del proveedor VPS con acceso administrativo autorizado. No crear shell genérica ni cambiar el `sshd` compartido. **No usar** la cuenta GitHub/Fleetia ni sus secretos.

## Orden de puertas, ninguna omitible

1. **Preflight documental y CI** de este candidato en PR y main con SHA exacto. Mantener Draft hasta revisión. La ejecución `plan` por GitHub no requiere secretos ni alcanza VPS; `stage` es distinta, exige autorización específica y prueba de protección del entorno GitHub.
2. **Custodia cloud exclusiva** de clave Ed25519 temporal: generación fuera del PC y VPS por un custodio autorizado (p. ej., entorno cloud del propietario), incorporación del privado como base64 al secreto de environment `SABORA_BOOTSTRAP_SSH_KEY_B64` sin mostrarlo ni entregarlo al modelo y de `known_hosts` previamente verificado como `SABORA_BOOTSTRAP_KNOWN_HOSTS_B64`. El environment debe contener también la variable pública `SABORA_BOOTSTRAP_CLIENT_ED25519_FINGERPRINT`, calculada fuera del runner y aprobada por el custodio, para vincular la clave de transporte Ed25519 sin frase de paso almacenada en el secreto; el workflow rechaza claves de otra clase o huella distinta. El environment también debe contener la variable pública `SABORA_BOOTSTRAP_HOST_ED25519_FINGERPRINT`, contrastada fuera de banda; el cliente exige un único pin `ssh-ed25519` de `146.59.145.64` y compara ese fingerprint antes de enviar un byte. Un secreto de repositorio compartido o un PAT con privilegios administrativos generales NO se recomienda; verificar la posibilidad de restringir por entorno y revisores. El `GITHUB_TOKEN` estándar no tiene permiso implícito para escribir secretos del repositorio: no diseñar una autoescritura ficticia.
3. **Pin SSH fuera de banda:** el custodio verifica la huella Ed25519 del servidor por un canal independiente y autenticado del VPS (no únicamente `ssh-keyscan` ni la misma conexión a validar), coteja el host/algoritmo con el pin de `known_hosts` y lo registra en el expediente. Las huellas observadas por Gateway son contexto, no certificación independiente automática.
4. **Receptor y pública limitados:** con autorización nominada y preflight de rutas Sabora, se instalaría `receive-v1.sh` **root-owned**, cuenta `sabora-bootstrap` con contraseña bloqueada, HOME 0700 y sin grupos adicionales, clave pública exclusiva con opciones **`restrict,command=...`** y ninguna otra clave ni ruta alternativa. Si la interfaz de Gateway para `ssh_authorized_keys.add` no permite opciones de restricción, **STOP**: no registrar una clave de shell general. No editar/reiniciar `sshd` compartido, Docker, nft, cuentas de terceros ni rutas ajenas. Inspección negativa de PTY, shell, forwarding, SFTP y SCP, además de prueba normal del receptor, antes de usar artefactos reales.
5. **Único `stage` autorizado:** GitHub Actions descarga el ZIP original de su artifact ID exacto, verifica SHA, CRC y ELF; envía bytes por **SSH normal directamente desde el runner a la cuenta Sabora**, el forced-command comprueba digest y el runner exige recibo exacto. Ante corte/fallo queda un archivo de cuarentena y **no hay reintento automático**. Si no hay clave o pin, la ejecución falla cerrada. No usa Gateway para trasladar binarios.
6. **Inspección posterior sin activar:** cotejar el archivo inerte y recibo, y solo después considerar instalación S43 bajo **otra autorización firmada**. El ZIP no es Node, Compose, source bundle, TLS, SQL, redes ni `installation.json`. El `stage` no instala el controlador ni pone `SABORA_RELEASE_AGENT_READY`.
7. **Retirada de identidad temporal:** cuenta `sabora-bootstrap` caduca el **28-11-2026**. Retirar clave GitHub y autorización SSH temporal tras reconciliar el resultado; con permisos y autorización propia, retirar cuenta/artefacto de cuarentena solo cuando su destino y estado sean conocidos. Si ha vencido, STOP antes de intentar SSH; nunca ampliar caducidad por inercia.

## Mantenimiento permanente posterior

Este bootstrap **no es** el canal permanente. El segundo mecanismo `sabora-maint` debe implementarse con credencial SSH **distinta**, forced-command root-owned, firma de propietario para cada upgrade/rollback del controlador, ledger durable, prueba A/B y recuperación por otra conexión, de acuerdo con [propuesta S47](https://github.com/jdlc86/CartaViva/blob/prep/sabora-offline-node-20261120/docs/architecture/SABORA_S47_CONTROLLER_MAINTENANCE_CHANNEL_CANDIDATE_2026-11-21.md) y decisión normativa pendiente. Ni el PC doméstico ni Gateway deben ser necesarios para su operación normal. El par propietario de **firma Ed25519** para consentimientos **no** debe residir en GitHub Actions, VPS, Git, chat o bajo la clave SSH de transporte. No confundir `sabora-release` (deploy de app) con `sabora-maint` (actualización del controlador).

## Evidencia y STOP final

**Código candidato** y pruebas estáticas/locales no son ejecución de GitHub Actions ni instalación validada. Antes de la primera transferencia real: autorización explícita de etapa, identidad/verificación de SSH independientes, receptor instalado con permisos revisados, environment protegido y secrets propios, hashes, CI SHA exacto; **Fleetia permanece intocable**. El hecho de tener `sabora-bootstrap` con HOME privado pero **0 claves SSH** sigue siendo un bloqueo material y no se corrige por crear este workflow.

### Prueba de frontera crítica añadida en S47-11 (candidata)

La CI del PR #79 incorpora `scripts/ci/sabora-cloud-bootstrap-sshd-lab.mjs` en el runner Linux desechable, **antes** del laboratorio general del controlador, para asegurar un usuario nuevo sin solapamientos. Usa OpenSSH real y forced-command `restrict,command=...`, con sustitución únicamente del digest de un paquete fixture que conserva el tamaño 8792 bytes. Negativas requeridas: shell arbitraria, pin de host falso, digest equivocado, entrada de 8793 bytes y replay. Positiva: archivo inerte en cuarentena de modo 0600, hash íntegro y recibo exacto. El mismo script de producción **no se instala** en VPS por pasar esta prueba. El contrato está en revisión; su aprobación requiere CI exitosa del SHA final.

La clave privada SSH del runner debe ser Ed25519 no interactiva y su fingerprint debe coincidir con `vars.SABORA_BOOTSTRAP_CLIENT_ED25519_FINGERPRINT`; no reutilizar la clave de autorización de firma de propietario. Un environment nombrado en YAML **no demuestra** que estén configurados revisores obligatorios ni secretos de entorno; éstos requieren comprobación administrativa por un custodio cloud, actualmente no disponible desde la conexión GitHub de esta sesión. Si no se demuestra protección, **STOP** antes de cualquier `stage`.
