## Recorrido y evidencia

- **GitHub.** El puente lee el Issue vivo en el repositorio autorizado y solo despacha el workflow gobernado existente. El workflow verifica checkout, ancestría, SHA exacto de main para deploy, y checks SUCCESS del SHA solicitado con fuente GitHub Actions. El artefacto de aplicación se busca en `ci.yml` con evento `push`, rama `main`, SHA, repositorio, resultado y asociación al run comprobados. El plan termina en el job de lectura, sin credenciales SSH ni acceso al host. `check-main` y el guard de CI se ejecutan antes y después del Environment para las operaciones.
- **Ruleset observada.** `sabora-rule` #27933106 está activa para `refs/heads/main`, con PR obligatorio, 0 aprobaciones exigidas, sin bypass, sin borrado ni force push. Los cuatro checks requeridos están vinculados a Actions (integración 15368). La API de rama devolvió `protected=true` y el SHA base de la tabla. El guard runtime comprueba protección booleana y SHA. La política y los secretos exclusivos de `sabora-live` se acreditan separadamente. [Ruleset](https://github.com/jdlc86/CartaViva/rules/27933106)
- **Host y transporte.** El cliente SSH usa clave dedicada, `known_hosts` anclado y protocolo cerrado. El lanzador fijo entrega el comando como datos a la entrada root V2. La instalación comprueba fuente/configuración, binarios, herramientas, reserva, runtime y permisos. El receptor verifica TTL, SHA, nombre, límite de cada frame y digest antes de admitir el bundle. El driver vuelve a comprobar montajes, ACL, tags, TAR, Compose permitido, red y nft bajo lock. El resultado exige readiness, HTTPS de ambas PWA, ACK correlacionado y reinspección. Rollback lee una versión healthy retenida y opera solo sobre la aplicación. El alcance de los controles se contrastó con `scripts/ops/sabora-release-{host-authorization-v2,installation-v2,receiver,controller,actuator,driver,local-inspector,readiness,ledger}.mjs`, sus dependencias y las pruebas.
- **Producto.** El diff completo contra main no cambia `apps/`, `packages/`, migraciones, Compose, lockfile ni `docs/design/`. Se conservan la composición aprobada, cliente/gestión, permisos, JWT/HMAC y la separación Stripe/externo. El gate funcional acredita trazabilidad. Las ejecuciones de PostgreSQL 17/Fastify/Chromium dan evidencia de laboratorio sin elevar los estados del inventario a aceptación.
- **Raíz de confianza.** GitHub y el secreto SSH propio autorizan el acceso de V2. El host valida el recibo, TTL, alcance y replay, pero el JSON carece de una prueba criptográfica independiente del actor. Permanece el riesgo de compromiso de cuenta, Environment, workflow o clave SSH. La reserva y las reglas root-owned aportan el alcance previamente aprobado, y el inspector compara su estado material. La prueba con testigo demuestra aislamiento en el runner.

## Puertas separadas para primera activación ficticia

1. **Aprovisionamiento V2 pendiente.** El repositorio contiene un exportador determinista de fuentes y derivación/verificación del manifiesto de la instalación por hashes. Falta el aprovisionador material reproducible que coteje el origen GitHub y componga de forma atómica fuentes, ELF, Node, Compose y configuración root-owned. Los ELF en cuarentena pertenecen a un SHA histórico. La preparación autorizada tendrá que verificar la cuenta y la clave SSH exclusivas, rutas/ACL/CA, binarios, configuración local de Docker y aislamiento de redes/puerto/nft antes de habilitar el indicador. [Contrato V2 §7](../architecture/SABORA_SIMPLIFIED_DEPLOYMENT_V2.md)
2. **Alertas pendientes.** `scripts/ops/sabora-release-readiness.mjs:105` comprueba ACK HTTPS V2 con SHA, correlación, hash de los bytes y fecha. La implementación receptora encontrada pertenece al laboratorio y no demuestra almacenamiento. La puerta productiva requiere un receptor Sabora que persista antes de emitir ACK y permita comprobar el registro correspondiente, más un ensayo de fallo que conserve `unknown`. Su integración debe usar un canal autorizado y la allowlist exclusiva.
3. **SQL pendiente.** El árbol contiene **103 migraciones**. El inventario local del SHA corregido produjo SHA256 `3b7bb1868b84381757ad257989e0472942bc08c11132d57a649fe633830e0712`. El CLI S46 genera inventario y su modo `observe` requiere operador aprobado, CA, endpoint directo `verify-full`, pin de clúster, PG17, `pgcrypto`, ausencia de objetos/roles/ledger Sabora y snapshot de solo lectura. La identidad soportada por ese modo es `postgres` fuera de Actions. Sigue pendiente acreditar el canal de lectura de menor privilegio. La alternativa de observador de S48-20 es condicional y tiene pendiente la autoridad heredada `TEMPORARY`. El antecedente TLS 1.3 no verifica CA/hostname. El snapshot tampoco excluye DDL de otras sesiones. Antes de migrar se requiere observación real, custodia, exclusión de DDL concurrente, autorización del árbol exacto y verificación posterior de ledger, permisos, RLS y HMAC. La afirmación de disponibilidad de la API no aporta por sí sola esas garantías. [Runbook S46](../runbooks/SABORA_S48_S46_AUTOMATED_DBA_READONLY_PREFLIGHT_CANDIDATE_2026-11-22.md)
4. **Aceptación pendiente.** Tras las autorizaciones y pruebas materiales sigue la comprobación de HTTPS, flujos reales de ambas PWA y aceptación humana visual/funcional. Stripe real permanece pendiente. La primera prueba se limita a datos ficticios con `backupPerformed=false`, `restorePerformed=false` y `realUsersAllowed=false`. La recuperación ordinaria deberá estar acreditada antes de admitir usuarios/datos reales o del siguiente release que la requiera.
