## 3. Puertas de decisión

**Propuesta de saneamiento, pendiente de decisión específica del propietario:** presentar un **solo lote administrativo de ocho PR candidatos**: #18–#22, #5, #17 y #4. Sus HEAD históricos pueden cerrarse **sin merge individual**, manteniendo sus ramas y el expediente GitHub con explicación de sustitución. **#8 permanece abierto** mientras falte el dictamen de seguridad específico (o consentimiento expreso sobre riesgo y alcance). La decisión no debe dejar que un test verde legitime restaurar el flujo `picked_up` obsoleto, ni debe exigir una prueba SQL de sincronización entre pestañas para fingir que el navegador consulta SQL directamente.

Para cualquier cierre posterior: reconsultar HEAD/estado exactos, registrar enlace a `main` y a CI y cerrar **sin merge ni borrado de ramas**, individualizando la motivación. No aprovechar el permiso previo para los 32 ancestros como permiso implícito para nueve divergentes.

**Más allá del saneamiento:** revisión independiente de #8 y del contorno de actor/capacidad, aceptación visual humana F28/R09 (la automática no equivale), Stripe sandbox y puertas de recuperación/activación. Estos pendientes no justifican versiones paralelas de la misma implementación en nueve ramas históricas, pero sí limitan lo que se puede afirmar del sistema.
