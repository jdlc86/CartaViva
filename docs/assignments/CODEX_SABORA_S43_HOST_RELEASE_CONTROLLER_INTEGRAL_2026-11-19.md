## 3. Arquitectura objetivo (propuesta de implementación)

```text
GitHub Actions (manual, main, plan sin SSH)
    | deploy/rollback: autorización Ed25519 + SHA + manifiesto + 6 hashes
    | SSH con known_hosts y clave exclusiva, protocolo acotado por stdin
    v
sabora-release (sin shell genérica, sin Docker, sin forwarding)
    | entrada fija, sin argumentos ejecutables ni rutas del cliente
    v
frontera privilegiada local mínima, root-owned (solo controlador Sabora)
    | verificación de instalación, scope, firma, reloj, lock, recepción
    | staging privado + revalidación de 6 expedientes + observación viva
    | validación de archivos TAR y Compose antes de primera mutación
    | ledger durable: consumo único antes de Docker
    v
núcleo executeScopedSaboraRelease + driver real de alcance cerrado
    | Docker solo imágenes/servicios permitidos por SHA; sin host global
    v
red interna API <-> web y gateway; ingress exclusivo 8443; egress cerrado
    | /ready + HTTPS 2 orígenes + alerta verificada + redes postrun
    v
ledger/historial durable + recibo de resultado saneado + retención
    | nueva autorización para revertir app a versión previamente saludable
```

### 3.1 Frontera de privilegios y provisioning no ejecutado

Proponer launcher root-owned y mecanismo de elevación de un **único comando fijo sin argumentos**, compatible con forced-command y manejo seguro de SSH_ORIGINAL_COMMAND. Preferir wrapper pequeño, sin shell interpretando payload y sin sudo general, sin SETENV ni permisos para Docker directo. Si se requiere alternativa, justificar su amenaza y equivalencia; no comprometer una cuenta SSH root genérica. Desactivar PTY, forwarding, agent/X11, túneles, subsistemas/SFTP, user rc y opciones de claves no admitidas. Resolver explícitamente la compatibilidad de cuenta no-shell con forced-command: no copiar una configuración nologin que impida el único comando permitido; prueba real de sesión en lab. Cuenta dedicada no miembro docker ni grupos privilegiados, no escritura sobre launcher, código, módulos, configuración, clave pública, estado, evidencias o staging privilegiado. Entradas stdout/stderr saneadas. No usar ubuntu, otra identidad SSH, sshd global ni reinicio de daemon. Si solución exige modificar configuración global compartida sin permiso/aislamiento, STOP.

Mantener rutas normativas HOST_RELEASE_PATHS: /etc/sabora/release/owner-public.pem, /var/lib/sabora-release/evidence, /srv/sabora/release/bundles, /var/lib/sabora-release/authorizations; /etc/sabora/release/runtime.env. Diseñar rutas adicionales únicamente dentro de raíces exclusivas, ownership/ACL/umask, checks de padres, O_NOFOLLOW, nlink, rutas canónicas, límites de espacio, protección TOCTOU y fsync. Distinguir staging verificado de bundle retenido. Instalar módulos runner/code separados del usuario de app UID/GID 10001 y su TLS. Proporcionar manifiesto de instalación por hash, plantilla de configuración sin secretos y receta de preflight e instalación paso a paso, idempotente y fail-closed; **no ejecutar en VPS**. Si el mecanismo se empaqueta, el artefacto de agente debe quedar autenticado contra SHA/árbol aprobado, no descargar/ejecutar código dinámico como root. No activar por una variable booleana, un fichero manipulable por SSH o un recibo de CI. En instalación ausente, inválida, parcial o no autorizada conservar STOP. No confundir funciones invocables del módulo con una frontera de autorización accesible al usuario SSH.
