# Sabora — contrato de despliegue simplificado V2 (decisión S50)

**Decisión del propietario, 23-11-2026:** sustituir para Sabora la autorización externa firmada Ed25519, los seis expedientes criptográficos y las nueve autoridades/claves diferenciadas de release por una gobernanza directa basada en identidad GitHub, SHA exacto, GitHub Actions protegido, SSH propio e inspecciones reales. **No se eliminan la autenticación SSH, los controles TLS, la integridad de artefactos, los permisos de ejecución ni el aislamiento absoluto de Fleetia.**

**Estado documental y técnico a 23-11-2026:** contrato candidato en [PR #85](https://github.com/jdlc86/CartaViva/pull/85), con **workflow, librerías, entrada root y tests V2 implementados en su rama**, pero **sin merge, aprovisionamiento de controlador V2 ni primera validación operativa en VPS**. El laboratorio Docker real histórico V1 no es certificación integral V2; el resultado CI solo corresponde a su SHA concreto. La instalación V1 —si existiera— no debe reutilizarse ni degradarse: permanece FAIL-CLOSED. Este documento no autoriza SQL, instalación, merge ni despliegue.

## 1. Ámbito y jerarquía

- Repositorio exclusivo `jdlc86/CartaViva`, **un restaurante**, dos PWA (cliente y gestión), único VPS físico compartido. **No tocar, consultar para operaciones, detener, reiniciar, modificar ni depender de Fleetia u otros proyectos**; sus credenciales, redes y contenedores permanecen fuera de alcance. Si el operador no puede demostrar aislamiento con verificaciones de recursos Sabora, detener la operación.
- Para el circuito de release, esta decisión **sustituye expresamente** las obligaciones V1 de firma independiente del propietario por operación, `installation.json` con firma Ed25519, seis `sabora-material-evidence/v2`, nueve fingerprints de custodios, `sabora-allocation-reservation/v1` firmado, ACK criptográfico obligatorio del custodio de alertas y firma DBA del preflight `sabora-initial-empty-preflight/v1`. Sustituye su formalismo documental, **no las comprobaciones físicas que representaban ni las autorizaciones específicas**.
- Son **ajenos** a la retirada: criptografía de JWT/Auth, HMAC de aplicación/comandas, TLS/SSH, integridad SHA256, autenticación de proveedores, firmas de webhook Stripe y mecanismos exigidos para datos económicos. No alterar estos controles.
- Las excepciones S45/S46 de primera activación con **datos exclusivamente ficticios**, aplazamiento de copias/restore y revisión interna siguen delimitadas al primer arranque de prueba. Sin usuarios ni datos reales hasta política ordinaria de respaldo y restauración probada. La S49 mantiene que no se requiere ordenador personal, Docker doméstico, Tailscale ni otro VPS para este hito.
- La **fuente normativa** de los requisitos funcionales y de seguridad continúa siendo la de `main` hasta que esta revisión esté integrada por decisión expresa; ningún handoff concede permisos.

## 2. Autorización única, no firma externa

1. **Identidad:** solicitudes exclusivamente del propietario GitHub `jdlc86` en el propio repositorio, mediante comando Issue acotado o `workflow_dispatch` protegido. Validar `github.actor`, autor real del Issue al momento de procesarlo, repositorio, evento, título, cuerpo vacío, rama y SHA completo exacto de `main`. El puente valida el Issue en vivo y lo cierra tras el intento de despacho; el controlador usa un identificador duradero derivado del **número de Issue original** y lo consume una sola vez, incluso ante reintentos o reruns. No confundir el acuse de despacho con el resultado de despliegue. No aceptar texto de PR, bots u otros usuarios como autorización.
2. **Código:** exigir checks reales SUCCESS de GitHub Actions sobre **el SHA idéntico** (incluidas pruebas integradoras y UI pertinentes), checkout fijo, paquete originado en push a `main` y manifest de SHA256 de todos los bytes de imágenes y Compose. Si `main` cambia o los checks no coinciden: STOP. Un check omitido o SKIPPED no vale PASS.
3. **Puerta de operación:** GitHub Environment exclusivo de Sabora (p. ej. `sabora-live`) limitado a `main`; secretos exclusivos del proyecto y permisos mínimos. Comprobar la protección efectivamente disponible; **no inventar revisión independiente** si el único propietario no dispone de otro aprobador. No ampliar permisos del `GITHUB_TOKEN`; no invocar operaciones de infraestructura por `push` a `main` ni como efecto colateral de CI.
4. **Transferencia:** SSH con clave distinta de Fleetia, usuario técnico exclusivo de Sabora, **comando forzado**, `known_hosts` anclado, sin shell abierta, SCP/SFTP genéricos, forwarding ni Docker socket para el usuario remoto. Mantener el listener SSH compartido inalterado. El canal cifra/autentica; no exige otra clave de **firma de aprobación** distinta de la clave de conexión.
5. **Registro:** un `authorizationId` derivado de run+intento GitHub para solicitudes manuales y de número de Issue original para solicitudes desde Issue, más operación/SHA fijados en el payload, exclusivo y duradero, aceptado una sola vez por el controlador; lock, journal y versión saludable anterior para rollback. El historial registra actor, GitHub run, SHA, digests, decisión y comprobaciones reales. **Registro técnico automático no equivale a expediente firmado a mano**. Un corte de transporte requiere reconciliación, nunca reintento ciego ni limpieza manual de ledger.

## 3. Instalación del controlador sin firma del propietario

- El primer aprovisionamiento requiere **autorización expresa del propietario**, independiente de autorizar un deploy, y una instalación acotada a rutas `/etc/sabora`, `/srv/sabora`, `/var/lib/sabora-release` y cuentas exclusivas. **No sustituir al operador autorizado por un runner con root/sudo genérico.**
- El paquete controlador incluye manifiesto determinista de GitHub con `repository`, `sourceSha`, SHA256 de fuentes, ejecutables Node y Compose, binarios compilados, configuración, herramientas y lista exacta. El instalador valida procedencia del artefacto CI, hashes, propietarios/mode/ACL, ausencia de symlinks o rutas writeable por usuarios no privilegiados y publica el árbol final de manera atómica; verificación posterior independiente y recibo de instalación **sin firma Ed25519 externa**.
- No se requieren `owner-public.pem`, clave del custodio, `installation.json` firmado ni nueve identidades criptográficas. Puede conservarse un **manifiesto de instalación simple root-owned** con valores SHA256 y procedencia para detectar alteración al iniciar el controlador. Su existencia **no certifica sola** el host: verificar archivos reales y parent directories en cada operación.
- El usuario técnico `sabora-release` y los roles mínimos **sí permanecen**: son identidades de autenticación/aislamiento necesarias, **no autoridades adicionales de firma**. Nunca reutilizar usuarios SSH, contraseñas ni claves de Fleetia.

## 4. Comprobaciones materiales automáticas que NO se eliminan

- **Supabase/SQL:** preflight real PostgreSQL 17 del proyecto restaurante: identidad/certificado con TLS `verify-full` y pin válido, observación de catálogo inicial Sabora vacío, ausencia de migración parcial/ledger, `pgcrypto`, control de concurrencia DDL/roles, migraciones append-only, comprobación posterior de roles mínimos/RLS/HMAC y acta de ejecución SHA+salida. La autorización de SQL y la del despliegue son actos distintos. **No se exige firma DBA ni wrapper criptográfico**, pero tampoco se acepta una afirmación sin consulta real. No introducir credenciales SQL administrativas en GitHub Actions mientras exista el conflicto de S38 ni reutilizar credenciales de otro proyecto; si el circuito existente no permite verificar/acceder con seguridad, STOP y resolverlo sin nuevo VPS ni ordenador doméstico.
- **Backup genesis:** primera activación con datos ficticios bajo aplazamiento S46 documentado como `backupPerformed=false`, `restorePerformed=false`, `realUsersAllowed=false`, y riesgo de pérdida aceptado. Es un estado de operación verificable sin `externalRestoreSha256` ficticio ni firma de excepción. Para siguientes releases reales restablecer backup externo y restauración real.
- **Aislamiento:** comprobar antes y después del deploy únicamente redes, contenedores, nombres de recursos, subredes/bridge y reglas nft **propias de Sabora**; ingress restringido y egress allowlist, servidor TLS específico, puerto aprobado; prueba negativa de bypass y de intento de operar recursos ajenos en laboratorio. Sin `docker compose down`, `prune`, `systemctl restart docker`, firewall global, `flush ruleset`, cargas o eliminaciones indiscriminadas. `docker compose up` solo con servicios, manifiestos e IDs exactos aprobados.
- **Integridad de carga:** validar los TAR Docker y el origen de las imágenes, digests previos y posteriores, Compose renderizado cerrado, configuración/secretos accesibles solo por roles Sabora y volumen/ACL privados. **Un SHA256 no sustituye esa inspección**. Si hay colisiones o rutas arbitrarias: STOP.
- **Alertas y salud:** observación efectiva y acuse correlacionado de receptor de alertas, readiness API y HTTPS de ambas PWA, aceptación funcional/visual humana independiente del resultado CI. No se exige custodio con clave Ed25519 de ACK, pero se exige entrega verificable y confiable.
- **Rollback:** solo una versión anterior de Sabora registrada healthy y retenida, operación GitHub explícita nueva, mismos límites de aislamiento/CI y datos; jamás revertir SQL ni actuar sobre otros proyectos. Primer deploy sin versión anterior no dispone de rollback.

## 5. Puertas de cambio de código y puesta en servicio

**Un solo recorrido autorizado.** No mantener V1 firmado y V2 sin firma como dos formas paralelas de operar el VPS. En el mismo hito técnico deben actualizarse coherentemente:

1. Normativa S38/S43/S46, contrato de release, runbooks y continuidad: quitar formatos y custodios criptográficos de la ruta obligatoria, preservar aislamiento, autorización separada SQL/VPS y excepciones genesis ficticias.
2. Workflow de deploy y puente Issues: retirar secretos `SABORA_APPROVAL_*` y `SABORA_APPROVER_PUBLIC_KEY_B64` y la etapa de autorización por firma; sustituirla por comprobación de evento owner + SHA + entorno + runId/nonce. No dar a `GITHUB_TOKEN` permiso excesivo.
3. Controlador raíz/receptor/instalación: retirar firmas y `verifyMaterialDossiers`, `assertDistinctReleaseAuthorities`, `verifySignedDocument` y configuración de seis custodios, reemplazándolos por un manifiesto **root-owned y digests verificados** y **preflight material real**. Mantener comando forzado, protección contra replay, journal, validación TAR, aislamiento vivo y ejecución limitada. Retirar rutas/módulos V1 muertos **solo después** de comprobar referencias; no dejar un bypass escondido.
4. Pruebas integradoras de extremo a extremo con PostgreSQL 17 y Docker aislados: positivo V2 completo; negativos para actor/Issue no autorizado, SHA/CI incorrectos, secret/key host incorrecto, sustitución de bundle, rutas inesperadas, red compartida, egress, operaciones Docker ajenas, rollback sin historial, repetición de runId, instalación parcial y fallo tras consumo. Verificar que las pruebas **ya no requieran firmas ni expedientes**, sin rebajar los tests de aislamiento.
5. Revisión técnica interna documentada (primera activación), checks exactos tras commit, aprobación de merge separada y verificación de comportamiento real. No declarar `GO deploy` por solo merge o PASS de laboratorio.

**Transición fail-closed:** mientras el controlador instalado/programado sea V1 o el V2 no esté completo y probado, el deploy sigue **NO-GO**; nunca forzar `SABORA_RELEASE_AGENT_READY`, sustituir un secret por cadena vacía, editar SSH global, ejecutar Docker por un atajo o desactivar temporalmente un test de seguridad. La firma se retira **del requisito de negocio**, no saltándola en la versión antigua.

## 6. Justificación y riesgo residual aceptado para el diseño

Este modelo reduce la necesidad de gestionar claves ajenas al canal SSH, firmadores offline y seis expedientes de terceros que no aportan separación humana real si todos los controla el mismo propietario. Se aproxima al circuito GitHub Actions + SHA + Environment + SSH de Fleetia **sin copiar sus privilegios de sudo ni su capacidad de operar recursos compartidos**.

**Estado comprobado de la protección (23-11-2026):** el propietario ha creado `sabora-rule` (ID GitHub `27933106`) y se ha leído posteriormente su configuración oficial: rama `main` protegida (`protected=true`), sin bypass, PR obligatorio con 0 aprobaciones, eliminación/force-push bloqueados y los cuatro checks `validate`, `web-publication`, `generate-lockfile` y `functional-ui-gate` vinculados a GitHub Actions. Esto **resuelve la configuración de rama pendiente** mencionada en el párrafo histórico siguiente, sin autorizar merge o deploy. Los cambios posteriores de la ruleset no se consideran aceptados sin nueva comprobación. El Environment `sabora-live` y su política de secreto/ramas aún **no están acreditados por esta lectura**.

**Requisito efectivo de `main` para V2:** la consulta real del 23-11-2026 encontró `main.protected=false` y ninguna ruleset listada. Como V2 retira la firma de autorización fuera de banda, el workflow incorpora `check-main` (consulta **solo lectura** a GitHub API, sin cambiar ajustes) y **rechaza `deploy`/`rollback`** si `main.protected!==true` o si su SHA difiere de `GITHUB_SHA`, tanto antes de `sabora-live` como tras pasar ese entorno. El modo `plan` sigue siendo de solo lectura y no exige protección. La comprobación runtime **no crea** protección de rama ni verifica los detalles de los permisos: previamente al primer deploy el propietario debe configurarla en GitHub, sin nuevos certificados, expedientes ni identidades. Mantener `main` por PR, prohibir force-push/deletions y asociar los cuatro checks integradores; comprobar que no existe bypass involuntario. No exigir un segundo revisor ficticio si el único operador es el propietario. Configurar `sabora-live` únicamente para `main`, con secretos SSH de Sabora y sin acceso de otros proyectos; comprobar materialmente los ajustes, que no se deducen de la existencia del nombre del Environment.

**Riesgo explícito:** con las firmas fuera de banda se elimina una defensa adicional contra compromiso de la cuenta GitHub, del Environment o del secreto SSH; GitHub y su canal de despliegue se convierten en la raíz de autorización. Requiere 2FA/passkey de la cuenta, protección efectiva de rama/entorno, permisos mínimos, revisión de cambios y credenciales exclusivas. Una firma externa no habría impedido por sí sola la mala configuración de redes o un `sudo docker` global: la defensa decisiva para Fleetia es el aislamiento del actuador, que aquí **no se elimina**.

**No se ejecuta nada por aprobar este diseño**: permisos de SQL, provisión en VPS, instalación, merge, primer deploy y aceptación son decisiones/operaciones separadas, concretas y verificables.

### Instalación V2: hashes materiales sin firmador ni expediente

La preparación V2 es **una sola instalación autorizada**, no un nuevo servicio. Utilizar el artefacto del SHA verificado de `main` generado fuera del VPS, un único juego de binarios C y Node/Compose controlados y rutas exclusivas `/etc/sabora` y `/var/lib/sabora-release`. No reutilizar la instalación V1 ni tocar el usuario, daemon, redes, imágenes o claves de Fleetia.

1. El operador autorizado verifica **antes de copiar** el SHA GitHub, el artefacto completo, las fuentes, binarios y el alcance de las rutas. Para la primera instalación, la cuenta Sabora/SSH forzado y los mounts/ACL son operaciones separadamente autorizadas. No permitir shell genérica ni `docker.sock` al usuario SSH.
2. Con los archivos **ya colocados por el aprovisionador autorizado como root-owned**, la función compartida `deriveControllerInstallationManifestV2({environment:'production'})` en `scripts/ops/sabora-release-installation-v2.mjs` deriva exclusivamente un manifiesto de SHA256 de los archivos de código, configuración, Node, lanzadores y herramientas **realmente presentes**. Rechaza archivos adicionales/faltantes, enlaces simbólicos y hashes de fuente divergentes. El resultado **no es una firma**: generar el JSON no certifica por sí mismo la procedencia. El operador coteja materialmente con el artefacto GitHub antes de publicarlo.
3. Publicar `/etc/sabora/release/installation.json` **una sola vez**, con contenido derivado y permisos root-only, mediante el mecanismo atómico autorizado. La entrada de producción ejecuta `verifyControllerInstallationV2({environment:'production'})`, compara los bytes y propietarios vivos con el manifiesto y rechaza todo drift **antes de recibir comandos**; no aceptar un `installation.json` V1 ni convertir su firma en un campo vacío.
4. Solo con el preflight de aislamiento real de Sabora, SQL/DBA autorizado y acreditado, receptor de alertas V2 realmente operativo y SSH/Environment propios, activar el indicador `SABORA_RELEASE_AGENT_READY=explicitly-provisioned-v2`. **No marcarlo** al terminar la generación del manifiesto. Prohibidos permisos globales sobre Docker/SSH o limpiar ledger para salvar un error.

**Prueba integradora:** el mismo laboratorio Docker/SSH desechable debe verificar un manifiesto V2 derivado de bytes reales y rechazar alteraciones de una fuente o la configuración antes de operar, además de ejecutar deploy y rollback V2, comprobar el servicio testigo ajeno y rechazar V1. Pasar el laboratorio no reemplaza la inspección y aprobación del VPS real.

### Restricciones que no se convierten en trámites

- **No hay firma fuera de GitHub, expedientes criptográficos, nueve custodios, ordenador personal, Codespace obligatorio, Tailscale ni otro VPS** para la primera activación ficticia. Tampoco se introduce otro controlador, otro workflow de deploy o un canal administrativo alternativo.
- Una solicitud **plan** no usa SSH, no ejecuta SQL ni cambia recursos. Un **deploy** no instala automáticamente el controlador, no ejecuta migraciones y no crea redes. Cada habilitación física excepcional (SQL, nft, reserva, instalación, deploy) requiere consentimiento específico del propietario. La autorización de **esta edición del PR** no extiende esos permisos.
- **Riesgo residual de la nueva raíz de confianza:** el servidor solo **autentica criptográficamente el canal por la clave SSH Sabora** y comprueba el payload canónico/alcance/expiración/ledger; el JSON V2 **no lleva firma externa** y el host **no consulta GitHub para autenticar por sí solo al actor**. Las comprobaciones de `github.actor`, Issue y CI las ejecuta Actions; si el token de workflow, el secreto SSH o el checkout confiable se comprometen, la firma adicional ya no aporta barrera. No afirmar defensa equivalente a Ed25519 offline.
- Prohibida cualquier operación genérica como `docker compose down`, `docker prune`, `systemctl restart docker`, `nft flush ruleset`, `pg_reset`, `DROP` o reinicio/reconfiguración de servicios de otro proyecto. Los recursos ajenos —incluido **Fleetia**— permanecen totalmente fuera de alcance.
- La recepción `sabora-alert-reception/v2` debe estar **realmente implantada y autenticada por HTTPS** con acuse correlacionado, mismo SHA, hash del contenido y fecha reciente antes de declarar `healthy`; cambiar V1 firmado por V2 sin receptor comprobado **no satisface** esa puerta.
- **No activar `SABORA_RELEASE_AGENT_READY` para forzar pruebas,** no sustituir secretos por valores vacíos, no usar una instalación V1 como V2 y no deducir autorización de la lectura de esta norma.

### Evidencia final breve y auditable, sin expedientes firmados

Para cada etapa basta un **registro técnico generado automáticamente** (no documento que el usuario deba firmar) con: repositorio, SHA/árbol de migraciones cuando aplique, actor GitHub y número de Issue o run, operación, digest del artefacto, verificación de aislamiento, preflight y postchecks materiales, estado de consumo, resultado y URL del run. No almacenar secretos, datos personales ni salidas SQL sensibles. El tablero y la continuidad solo recopilan el estado verificable del hito, no son autorizadores. En el primer despliegue de prueba anotar explícitamente `backupPerformed=false`, `restorePerformed=false` y `realUsersAllowed=false`; nunca atribuirles valor de backup o seguridad técnica contra usuarios reales.

**Regla GO/NO-GO:** solo puede decirse `GO para activar` si CI exacta, código V2 revisado, instalación V2 verificada, SQL autorizado y realizado, aislamiento real, alerta autenticada y aceptación de ambas PWA cumplen. Una autorización, un PR abierto, un test con fixture o un 200 HTTP aislado no equivalen al cumplimiento.

## 8. Decisión S51 — un único ejecutor DBA temporal Sabora en el VPS existente

**Decisión de diseño expresamente aprobada por el propietario el 24-11-2026 («Ok adelante» a la solicitud específica de ubicación y credencial administrativa).** Candidata en PR #87; entra en vigor solo tras integración autorizada. No autoriza ejecución, provisión, transferencia de secretos, SQL, ni deploy.

Para la primera activación ficticia, se sustituye únicamente la ubicación off-host exigida por el runbook S48/S46 por un proceso Linux temporal **sin privilegios de root, sin socket Docker, sin mounts/redes de otros proyectos**, en ámbito exclusivo de Sabora del VPS existente. No se instala otro controlador, servicio permanente, máquina, workflow ni equipo doméstico. La autorización de provisión y ejecución en VPS es separada; si no hay aislamiento o canal autorizado de credenciales, STOP. La separación física requerida para backup/restore ordinario no se modifica.

**Identidad DBA:** el observador actual exige la cuenta `postgres`; no equivale a una credencial estrictamente read-only como exige §7. Decisión acotada: admitir excepcionalmente la identidad DBA existente de RESTAURANTE para la observación inicial, solo desde el operador temporal autorizado y exclusivamente con `REPEATABLE READ READ ONLY`, `default_transaction_read_only=on` y SQL fijo revisado. No crear un rol observador previo que contradiga el catálogo inicial vacío.
