# Sabora — candidato de despliegue gobernado y red exclusiva V1

**Estado: propuesta normativa en PR #59, NO integrada ni operativa.**
**Propietario: decisión 14-11-2026.** Un restaurante Sabora, dos PWA independientes, un único VPS compartido; no existen usuarios reales. Este texto desarrolla la petición de un despliegue automatizable y gobernado **sin sustituir** los contratos de [aislamiento](CARTAVIVA_PROJECT_BOUNDARY.md), [autorización](../SABORA_AUTHORIZATION_GATE.md), [validación y recuperación](SABORA_VALIDATION_OBSERVABILITY_METHOD_V1.md), [ciclo P3](../runbooks/SABORA_P3_ISOLATED_LIFECYCLE_RUNBOOK_2026-10-29.md) ni [primera activación](../runbooks/SABORA_S38_FIRST_OPERATIONAL_ACTIVATION_RUNBOOK_2026-11-12.md). Un conflicto es STOP y requiere decisión del propietario, no reinterpretación.

## 1. Contrato de gobernanza: no convertir CI en permiso de publicar

La operación se **dispara exclusivamente** mediante `workflow_dispatch` del repositorio `jdlc86/CartaViva`, desde `main`, con operación `plan`, `deploy` o `rollback` y SHA completo que pertenezca a la historia de `main`. No hay despliegue en `push`, PR, cron ni por terminar CI. `plan` nunca contacta al VPS.

- **CI del SHA exacto:** exigir cuatro jobs finalizados en SUCCESS: `validate`, `web-publication`, `generate-lockfile` y `functional-ui-gate`. `CV005+B2 opt-in` y `visual-final-acceptance` no se interpretan como PASS si están SKIPPED; la evidencia DBA y la aceptación humana deben aportarse adicionalmente.
- **Aprobación externa vinculada a operación y SHA:** artefacto canónico `sabora-governed-release/v1`, con ID de autorización único, ventana no superior a una hora, origen(es) aprobados, host y servicio(s) exactos, y seis referencias SHA256: restauración externa real, puerta SQL real, control ingress, enforcement egress, recepción de alertas y revisión independiente. Su firma **Ed25519** se verifica con clave pública previamente custodiada y aprobada. El workflow enviaría al host **por stdin SSH cifrado** el JSON de autorización y su firma; el agente instalado debe **revalidar** la firma con una clave pública local root-owned, contrastar los hashes con los expedientes reales y rechazar autorizaciones previamente consumidas. El control realizado solamente en Actions no basta. La firma solo acredita la declaración del custodio; **las evidencias reales deben ser revalidadas en el host por el controlador** antes de actuar. Nunca generar hashes ficticios para desbloquear.
- **Puerta de entorno separada:** `sabora-live` en GitHub Actions. Según plan/licencia, los reviewers obligatorios pueden no estar disponibles en repositorios privados; por ello el gate de firma **NO depende** de que GitHub ofrezca esa protección. Nadie debe afirmar que la protección nativa está activada sin comprobarla. La clave privada del firmante nunca se almacena en Actions, el VPS, Git, los logs ni ChatGPT.
- **Sesión de operación separada:** el workflow pide un usuario SSH futuro `sabora-release`, **sin shell genérica ni acceso al grupo Docker**, exclusivamente con un `forced-command` instalado por un operador autorizado. La huella SSH del host debe estar anclada mediante `known_hosts`, sin `StrictHostKeyChecking=no`. **No reutilizar la identidad SSH `ubuntu` o Fleetia.** La cuenta, el comando fijado, sus ACL y el repositorio de imágenes aún NO están provisionados.
- **Fallo cerrado:** el job `execute` requiere `SABORA_RELEASE_AGENT_READY=explicitly-provisioned`, clave pública aprobada, autorización firmada correspondiente al SHA/operación, y credenciales SSH restringidas. Sin cualquiera de ellos, no puede ejecutar la operación. La mera existencia del workflow o de los secretos Origin CA no permite instalar.

**Firma local reproducible, sin enviar claves:** [\`scripts/ops/sabora-sign-release-approval.mjs\`](../../scripts/ops/sabora-sign-release-approval.mjs) firma un JSON de evidencia con Ed25519 **fuera de Git y del VPS**, en un equipo del propietario que conserve la clave privada en un archivo restringido. Rechaza firma con SHA/host/orígenes/ventana inválidos y seis hashes idénticos. Emite JSON canónico, firma base64 y clave pública en un directorio externo al checkout, nunca imprime la clave privada. El operador custodia el par de secretos de autorización y configura en GitHub las variables habilitantes **solo tras revisión/permiso**. La firma no crea por sí misma un restore ni un firewall: los hashes han de corresponder a seis expedientes **realmente verificados**.\n\n**Modelo de registro/rollback:** el futuro agente debe poseer un ledger **solo Sabora**, atómico, con `authorizationId` consumible una única vez, versión previa, SHA + digests de imágenes, evidencias de gates y estado/postchecks. `rollback` requiere aprobación firmada nueva y solo revierte aplicación/imagen a una versión previamente registrada; **no revierte SQL ni elimina datos**. No usar `docker compose down`, `prune`, reinicios globales, wildcard ni mutaciones de otros proyectos. Un despliegue fallido no puede desencadenar automáticamente una acción fuera de su autorización.

## 2. Automatización por etapas, sin desproteger el servidor

1. **Plan:** GitHub Actions prueba SHA/ascendencia, jobs de CI y compila el conjunto de recursos admitidos: proyecto Compose exactamente `sabora`, archivos `compose.sabora-operational.yml` + `compose.sabora-web.yml`, servicios `sabora-egress`, `api`, `web` y host `146.59.145.64` en TCP/8443. El plan registra STOP de puertas externas.
2. **Aprobación:** responsable autorizado verifica de forma material backup externo restaurable, alcance SQL/roles/HMAC, TLS, 2 PWA, alertas/receptor, ingress y egress bloqueado; la firma limita operación, SHA, host y ventana. El equipo DBA y propietario mantienen autorizaciones independientes de migración/backup/merge/despliegue.
3. **Preparación:** operador con acceso exclusivamente Sabora instala previamente el agente `forced-command` root-owned y configura un mecanismo **inmutable, trazable y por digest** para entregar código/imágenes al VPS. La acción actual **no instala ni implementa ese agente y no entrega artefactos de runtime**; faltan los digests y el canal, por lo que **no es apta aún para ejecutar despliegues**.
4. **Aplicación controlada:** solo cuando el agente esté realmente implantado y verificado, este debe comprobar **de nuevo** la aprobación y los seis expedientes, hash de artefactos, pertenencia exclusiva de redes y puerto, entorno SQL y ausencia de reglas amplias; ejecutar únicamente las operaciones Compose nominadas y supervisar readiness real, HTTPS de los dos hostnames, fallos, auditoría y alertas.
5. **Cierre o reversión:** dejar ledger y evidencia de ejecución real, diagnóstico y flujos con datos ficticios; verificar parada y reversión Sabora-only, sin dependencias de proyectos ajenos. La aceptación visual/funcional por el propietario es separada del éxito de CI y del 200 en `/ready`.

## 3. Ingress exclusivo y egress cerrado

La fase de red **aún no está configurada**. El preflight de solo lectura en el VPS identificó rutas `172.17.0.0/16` y `172.18.0.0/16` (sin consultar redes ajenas por nombre); puerto 8443 libre, 80/443 ocupados y nftables. Se ensayó `docker.create_network dry_run` para el **nombre exclusivo `sabora_ingress_filtered`**, bridge, IPv4 candidata `172.28.240.0/24`, gateway `172.28.240.1`, sin IPv6 y sin attachable. `wouldChange=true` y `changed=false`: **no se creó la red**. La ausencia de intersección en rutas **no garantiza** ausencia de redes Docker no activas ni contención externa; repetir preflight antes de crear.

[`scripts/ci/sabora-ingress-network-policy.mjs`](../../scripts/ci/sabora-ingress-network-policy.mjs) genera **solo un candidato** de tabla nftables `inet sabora_ingress_guard` para el **bridge concreto** obtenido tras provisionar y verificar la red exclusiva. Exige rangos de origen Cloudflare explícitos (nunca `0.0.0.0/0`), rechaza flujos entrantes nuevos que no provengan del proxy autorizado y bloquea conexiones nuevas **desde ese bridge** al exterior. Las reglas de otros proyectos quedan fuera del alcance y no se autoriza `flush ruleset`. **NO ejecutar este fichero como firewall:** el generador no valida cadena/hook de nftables existente, persistencia tras reinicio, dinámica de rangos Cloudflare, reglas del proveedor ni reversión real. Antes de aplicar:
- Obtener rangos Cloudflare de la fuente oficial y verificar mantenimiento; probar IPv4 y IPv6 según origen, direct-to-origin denegado y ruta HTTPS 8443. No cambiar `SSL/TLS`, puerto 443 o proxy compartido.
- Ejecutar `nft --check` sobre una configuración **acotada** y probar inbound legítimo, denegación de bypass, denegación de salida nueva, tráfico establecido y supervivencia de otros servicios en un entorno desechable. El operador debe demostrar rollback solo de la tabla Sabora, sin borrar cadenas generales.
- Egress externo debe tener red filtrada **separada** para `sabora-egress`, con destinos y puertos PostgreSQL/JWKS/alertas aprobados; **el aislamiento ingress no sustituye enforcement egress** ni basta con nombres de redes Docker.
- El proyecto Compose no debe crear libremente ambos bridges. Las redes ingress/egress externas se provisionan **solo cuando están respaldadas por enforcement independiente**, comprobando ausencia de colisiones y ACL. No conectar a ninguna red ajena, ni inspeccionar contenedores de Fleetia.
- No declarar aislamiento completo por la creación de una red vacía, IP dedicada, ACL del certificado, reglas parciales o CI.

### Reconciliación de seguridad del corte S40-2 (14-11-2026)

- Se ha separado el flujo de deploy del rollback **sin depender de la caducidad de artefactos Actions**. Deploy requiere el paquete binario de un CI push a main del SHA exacto; rollback no descarga ese paquete: envía solo una solicitud firmada, y depende de una versión anterior de Sabora retenida, verificada y reflejada en un ledger confiable del host. Ese ledger/observador **no está instalado**; si falta, la operación rechaza.
- El nuevo enrutador de host, scripts/ops/sabora-release-host-router.mjs, decide el tipo de solicitud desde el comando SSH exacto. En rollback verifica la firma antes de invocar cualquier lectura de historial u observación de runtime, y ambas se consideran **fuentes protegidas que el operador autorizado aún debe implementar**. No permite SSH interactivo ni Docker.
- El verificador de cuatro jobs CI también exige ahora que el origen de cada check-run sea la aplicación oficial GitHub Actions (app.slug=github-actions). Se comprobó el campo en checks reales del repositorio antes de codificar la condición.
- Todas las pruebas que se ejecuten en CI siguen siendo de código/fixtures desechables. No existe aún un histórico de versiones reales con estado saludable, un retorno demostrado del proceso ni supervisión y alertas reales en el VPS. El enrutador operativo termina en STOP incluso si el mensaje es legítimo.

**SHA candidato de código de seguridad más reciente: 4c0566825c653bbaf759f90fd11df828889517bc.** Solo marcar pruebas PASS si los workflows de ese SHA concluyen y se inspeccionan. El PR continúa Draft y no autoriza merge ni uso de recursos del VPS.
